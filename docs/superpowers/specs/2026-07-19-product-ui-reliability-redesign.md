# 혜니캘린더 제품 UI·신뢰성 전면 정비 설계

## 배경과 관측 근거

혜니캘린더는 로즈·민트·라벤더 색상과 3D 클레이 자산을 중심으로 가족 간의 다정한 연결이라는 고유한 인상을 이미 갖고 있다. 역할 선택, 부모 로그인, 아이 홈의 핵심 화면은 따뜻하고 친근하다. 이번 정비는 이 정체성을 버리는 재디자인이 아니라, 실사용 안정화 단계에 맞춰 정보 계층·상태 피드백·접근성·성능을 하나의 제품 시스템으로 통제하는 작업이다.

2026-07-19 현재 코드와 360×800·390×844 모바일 브라우저 기준선을 확인한 결과는 다음과 같다.

- `src` 아래 CSS 70개에 `font-size` 974개·고유값 45개, `border-radius` 785개·고유값 53개, `box-shadow` 366개·고유값 204개가 존재한다.
- 글꼴 크기 선언의 93.1%가 토큰을 사용하지 않고, 글꼴 블록의 86.2%가 명시적 행간 없이 브라우저 기본값에 의존한다.
- 12.5px 이하 글자와 낮은 대비 색상이 결합된 블록이 최소 145개다. 현재 `--fg-muted`는 앱 배경 위 3.64:1, `--fg-faint`는 2.41:1이며 로그인 placeholder는 약 2.01:1이다.
- 실제 버튼 CSS를 TSX와 교차 확인했을 때 양쪽 크기가 44px 미만인 클래스가 최소 57개다. 공통 아이콘 버튼도 42×42px다.
- Lucide 아이콘은 77종, 직접 렌더 294회이며 크기가 11~52px로 분산돼 있다. 같은 기능 수준의 아이콘도 크기와 굵기가 다르다.
- 이미지 105개는 모두 정상 디코딩되고 깨진 정적 참조는 없지만, 실제 사용 중인 `status/safe.webp`에 체크무늬 배경이 포함돼 있고 장소·안전지표 자산의 optical size가 불균형하다.
- 미사용 이미지 12개 약 499KB와 동일 파일 중복 1쌍이 PWA precache에 포함된다.
- 전체 라우트가 `App.tsx`에서 정적으로 import되어 현재 main JS가 약 996KB, CSS가 약 374KB이며 Vite의 500KB chunk 경고가 발생한다. PWA precache는 약 5.5MiB다.
- 로그인·OAuth는 일부 경로에 요청 제한시간이 없고, 버튼은 문자열만 바뀌어 대기 상태가 충분히 보이지 않는다. 빈 ID·비밀번호도 클라이언트 검증 없이 일반 인증 오류로 귀결된다.
- `DailySafetyReport`와 `WeeklyFamilyReport`는 조회 실패를 빈 배열로 바꿔 `0건` 또는 안전한 상태처럼 표시할 수 있다.
- 아이 홈의 경로 버튼은 `/route`로 이동하지만 현재 라우트는 부모 역할 아래에만 있어 아이가 사용할 수 없다.
- 상세 화면의 `navigate(-1)` 의존은 푸시·딥링크 진입 시 앱 밖이나 잘못된 화면으로 돌아갈 수 있다.
- baseline은 `npm run typecheck`, 534개 Node 테스트, `npm run build`, high 이상 `npm audit`를 통과했다. 반면 `scripts/*.spec.ts`는 오래된 import·계약 때문에 20개 중 13개가 실패해 공식 품질 게이트로 사용할 수 없다.

## 선택한 방향

기존 브랜드 정체성을 유지하는 **시스템 수준 프리미엄 정비**를 선택한다.

- 유지: 로즈·민트·라벤더·골드의 의미 체계, 3D 클레이 이미지, 부모와 아이의 역할별 말투, 핵심 홈 구조, Lucide와 3D 이미지의 이원화 원칙.
- 축소: 모든 카드의 과도한 radius·border·넓은 shadow, 중복 설명, 지나치게 작은 캡션, 화면별 매직 넘버, 장식 목적의 원시 이모지.
- 강화: 오류와 대기 상태의 정직한 표시, 명확한 주요 행동, 44px 터치 영역, 읽을 수 있는 대비, 일관된 뒤로가기, 화면별 데이터 신뢰 상태, 초기 로딩 성능.

전체 브랜드를 바꾸는 시각 재구축이나 구조가 다른 새 앱을 만들지 않는다. 기존 사용자의 학습과 실사용 동선을 보존하면서 가장 위험한 상태·기능 문제부터 수정하고 공통 토큰을 화면에 단계적으로 적용한다.

## 목표

1. 사용자가 탭한 모든 비동기 행동에서 즉시 대기 상태를 보고, 성공·실패·재시도 가능 여부를 이해할 수 있게 한다.
2. 조회 실패를 빈 데이터나 안전한 상태로 위장하지 않는다.
3. 부모·아이 역할과 활성 아이 선택을 보존하면서 경로·뒤로가기·딥링크를 안정화한다.
4. 타이포그래피, 간격, radius, shadow, 아이콘을 작은 의미 체계로 통합한다.
5. 일반 텍스트와 컨트롤은 WCAG 2.2 AA 대비·포커스 기준을 만족하고, 터치 컨트롤은 제품 기준 44×44px 이상을 확보한다.
6. 불필요한 설명을 짧은 제목·보조 문구·아이콘·점진적 공개로 바꾸되, 안전·동의·법적 정보는 삭제하지 않는다.
7. 초기 JS·PWA 자산 비용을 줄이고 화면 전환 중 빈 화면 대신 공통 skeleton을 표시한다.
8. 자동 검증, 모바일 브라우저, A17 부모 모드, razr 아이 모드에서 확인된 결과만 출시 후보로 인정한다.

## 비목표와 안전 경계

- `hyeni-1` Worker를 재구축하거나 API 응답·D1 스키마를 추정해 변경하지 않는다.
- 새 UI 라이브러리, 외부 폰트 CDN, 분석 SDK를 임의로 추가하지 않는다.
- 선생님 모드를 프로덕션에 노출하지 않는다.
- 부모 홈에만 있는 활성 아이 선택 원칙과 member id/user id 구분을 변경하지 않는다.
- 일정·준비물·메모·위치·세션의 기존 보안 불변식을 우회하지 않는다.
- refresh 토큰을 출력·외부 회전·복사하지 않는다.
- 계정 데이터, 페어링, 앱 데이터는 삭제하지 않는다. Android 설치는 `adb install -r`만 사용한다.
- S25는 이번 검증과 설치에서 계속 제외한다.

## 시각 기반 시스템

### 타이포그래피

Pretendard Variable을 기본으로 유지하고 Jua는 아이 화면의 감성 제목에만 제한한다. 의미 역할은 다음 9단계로 통합한다.

| 역할 | 크기/행간 | 굵기 | 사용처 |
|---|---|---:|---|
| Display | 32px/1.2 | 800 | 온보딩 핵심 문구, 특별 완료 화면 |
| Title XL | 24px/1.25 | 800 | 탭 화면 최상위 제목 |
| Title L | 20px/1.3 | 800 | 상세 화면 제목 |
| Title | 18px/1.35 | 700 | 카드·모달 제목 |
| Body L | 16px/1.5 | 600 | 주요 설명·강조 값 |
| Body | 15px/1.5 | 500 | 일반 본문·입력 |
| Body S | 14px/1.45 | 500~600 | 보조 본문 |
| Label | 13px/1.4 | 700 | 폼·칩·버튼 보조 라벨 |
| Caption | 12px/1.4 | 600 | 메타데이터·시간 |

- 핵심 정보·탭·입력·버튼에서 12px 미만을 금지한다.
- SOS, 축하 숫자, 타이머만 40·48·64px display 예외를 허용한다.
- 굵기는 500·600·700·800을 기본으로 하고 모든 라벨이 800 이상으로 경쟁하지 않게 한다.
- `body`에 기본 행간을 두고 다행 본문은 의미 토큰으로 행간을 명시한다.

### 색과 대비

- 읽을 수 있는 보조 글자색을 별도 토큰으로 두고 현재 `fg-faint`는 선·장식·disabled에만 사용한다.
- 입력 placeholder도 일반 본문과 구분되면서 4.5:1을 만족하는 색을 사용한다.
- 각 accent에 `on-solid`와 `on-soft`를 분리한다. 밝은 gradient 위에 흰색 일반 글자를 무조건 올리지 않는다.
- 위험, 성공, 주의 상태는 색만으로 구분하지 않고 아이콘·짧은 라벨을 함께 제공한다.
- disabled는 낮은 대비를 허용하되 활성 행동처럼 보이지 않아야 하고, 설명 텍스트에는 disabled 색을 사용하지 않는다.

### 간격

primitive spacing은 `2(optical) / 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48`로 제한한다.

- compact gutter 16px
- 일반 화면 gutter 20px
- 온보딩 gutter 24px
- 아이콘과 텍스트 6px
- 컨트롤 사이 8px
- 카드 내부 16px 또는 20px
- 섹션 사이 24px
- 큰 페이지 구획 32px

부모·아이 화면의 밀도 차이는 유지하되 같은 역할의 헤더·카드·행은 같은 semantic spacing을 사용한다.

### Radius와 elevation

- radius: `8 / 12 / 16 / 20 / 24(sheet only) / pill`
- 일반 카드 최대 16px, hero·modal 20px, bottom sheet 상단 24px를 사용한다.
- 기본 카드는 border만 사용하고 넓은 shadow를 제거한다.
- soft, floating, modal의 세 단계 shadow만 둔다.
- 브랜드색 shadow는 핵심 hero나 주요 CTA에만 제한한다.
- 장식용 3D blob, 원형 avatar, status pill은 일반 카드 규격의 예외다.

### 아이콘과 이미지

Lucide glyph 크기와 버튼 hit area를 분리한다.

| 역할 | glyph | stroke | hit area |
|---|---:|---:|---:|
| 메타·칩 | 16px | 2.2 | 행 전체 또는 44px |
| compact row | 18px | 2.2 | 44px |
| 기본 action | 20px | 2.2 | 44px |
| navigation | 22px | 2.2~2.4 | 44px |
| 강조 action | 24px | 2.4 | 48px 이상 |

- 기능·hero는 3D WebP, 텍스트 행·유틸리티는 Lucide를 사용한다.
- OAuth 브랜드 심볼과 아이 모험 지도 경로의 inline SVG는 유지한다.
- `ParentLocation`의 유틸리티 inline SVG와 의미 아이콘 슬롯의 원시 이모지는 해당 Lucide 또는 기존 3D 정본으로 교체한다.
- 부모 하단 위치 탭의 Lucide `MapPin`은 현재 규칙과 이력에 맞는 정본이므로 유지한다.
- `status/safe.webp`는 체크무늬가 없는 투명 원본으로 교체한다.
- 장소 6종과 안전지표 4종은 동일 슬롯에서 피사체가 비슷한 optical size로 보이도록 캔버스를 정규화한다.
- 미사용·중복 이미지는 실제 참조와 PWA manifest를 확인한 뒤 제거한다.
- 네트워크 사진은 고정 비율, `loading="lazy"`, `decoding="async"`를 적용하고 첫 화면 hero는 eager로 유지한다.

## 공통 상호작용과 상태 계약

### 비동기 버튼

모든 저장·로그인·조회 요청 버튼은 다음 계약을 공유한다.

1. 탭 즉시 spinner와 진행 동사를 표시한다.
2. 처리 중 버튼을 비활성화하고 중복 요청을 막는다.
3. 버튼 폭과 핵심 레이아웃이 바뀌지 않는다.
4. 성공 시 서버 응답 또는 정본 캐시 반영을 확인한 뒤 완료 상태를 보여준다.
5. 실패 시 버튼을 다시 활성화하고 화면 안의 구체적 오류와 재시도를 제공한다.
6. 네트워크 요청은 기존 API 호출 특성에 맞는 제한시간을 갖고, 사용자 취소·화면 정리 후 늦은 응답이 상태를 덮지 않는다.
7. OAuth 외부 브라우저 전환은 앱 복귀·취소 시 busy가 풀리는 별도 수명주기 계약을 갖는다.

ID 로그인은 공백 ID·비밀번호를 요청 전에 검증하고 각 필드에 자연스러운 오류를 표시한다. 인증 실패, 네트워크 실패, 서버 지연을 같은 문구로 합치지 않는다.

### 화면 데이터 상태

모든 서버 조회 화면은 `loading / refreshing / success / empty / error / unavailable`을 구분한다.

- 첫 로딩: 화면 구조를 반영하는 skeleton 또는 공통 status를 표시한다.
- 백그라운드 갱신: 기존 데이터를 유지하고 작은 갱신 표식만 보인다.
- empty: 성공 응답의 빈 데이터일 때만 표시한다.
- error: 마지막 정본 데이터가 없으면 오류·재시도 UI를 표시한다.
- stale: 마지막 정본이 있으면 업데이트 시각과 갱신 실패를 함께 표시하고 안전 상태로 단정하지 않는다.
- entitlement unavailable: 위치·구독 정본을 확인하지 못한 경우 캐시 좌표나 프리미엄 데이터를 열지 않는다.

`DailySafetyReport`와 `WeeklyFamilyReport`는 각 구성 query의 실패를 별도로 추적한다. 필요한 데이터가 실패하면 `0건`, `안전`, `문제없음`을 계산하지 않고 해당 섹션을 확인 실패 상태로 닫는다.

### 모달·포커스·키보드

- 전역 `:focus-visible` ring을 제공하고 `outline:none`을 쓰는 입력·버튼은 같은 규칙으로 대체한다.
- modal은 `role="dialog"`, `aria-modal="true"`, 접근 가능한 제목을 갖는다.
- 열릴 때 첫 안전한 컨트롤로 포커스를 이동하고, Escape로 닫으며, 닫은 뒤 트리거로 포커스를 돌린다.
- destructive action은 기본 포커스를 받지 않는다.
- loader는 `role="status"`와 적절한 `aria-live`를 사용한다.

## 라우팅과 역할 계약

### 아이 경로 화면

`/route`는 부모와 아이가 모두 접근 가능한 공유 route로 이동한다.

- 부모는 현재 활성 아이 또는 명시된 `child` hint만 사용한다.
- 아이는 본인 `user_id`와 일치하는 child member만 사용한다.
- 유효한 대상이 없으면 첫째로 폴백하지 않는다.
- 헤더 문구와 홈 fallback은 역할별 존댓말·반말과 `/parent/home`·`/child/home`을 사용한다.

### 안전한 뒤로가기

푸시·딥링크로 직접 열린 상세 화면은 브라우저 history의 존재를 추정해 무조건 `navigate(-1)` 하지 않는다. 공용 helper가 앱 내부 진입 여부를 확인하고 다음 우선순위를 적용한다.

1. 명시적으로 전달된 안전한 return route
2. 현재 앱 세션에서 확인된 내부 history
3. 역할별 홈 fallback

로그인·외부 URL·다른 역할 route는 return target으로 허용하지 않는다. 뒤로가기 없는 `ParentFamily`에도 같은 공통 affordance를 제공한다.

## 화면 정보 구조

- 부모 홈: 아이 상태·오늘 일정·안전 신호·주요 행동을 먼저 두고, 긴 설명은 `attention` 상태 또는 상세 화면에서만 연다.
- 아이 홈: 현재 시간대 행동·오늘 준비·부모와의 연결·SOS를 우선하며, 장식이 행동을 가리지 않게 한다.
- 목록·설정: 한 행에 하나의 주요 의미와 하나의 다음 행동만 둔다. 반복 설명은 section helper로 한 번만 제공한다.
- 보고서: 숫자 요약과 근거 목록을 분리하고, 조회 실패는 숫자로 환산하지 않는다.
- 안전·동의·구독: 위험·비용·아이 알림·자동 종료 같은 신뢰 문구는 아이콘으로 대체하거나 숨기지 않는다.
- 빈 상태: 장식 이미지, 짧은 제목, 한 문장 설명, 필요한 경우 하나의 CTA만 둔다.

## 성능과 자산 로딩

- 화면 component를 route 단위 `React.lazy`로 분리하고 공통 `Suspense` fallback을 둔다.
- 인증 provider, shell, 현재 역할의 첫 화면에 필요한 코드는 공통 chunk에 유지하고 사용하지 않는 역할·상세 화면은 초기 chunk에서 제외한다.
- 자산 삭제는 정적 참조·동적 매핑·manifest·service worker precache를 모두 확인한 뒤 수행한다.
- 2MB Pretendard Variable은 오프라인·한국어 glyph 보존을 우선한다. 실제 glyph coverage와 Android 렌더를 확인하지 않은 서브셋 교체는 하지 않는다.
- 빌드 후 main chunk와 전체 precache를 baseline과 비교하고, 새 chunk가 화면 전환을 막지 않는지 느린 네트워크에서 확인한다.

## 테스트와 검증 설계

### 자동 회귀

- 새 기능·버그는 테스트가 먼저 실패하는 것을 확인한 뒤 최소 구현한다.
- 로그인 검증·timeout·busy 상태, 보고서 error aggregation, 역할별 route 대상, 안전한 뒤로가기, modal 접근성 계약을 테스트한다.
- 디자인 토큰 테스트는 핵심 글자가 12px 미만인지, interactive hit area가 44px 미만인지, 허용되지 않은 직접 아이콘 SVG·원시 이모지가 있는지 감시한다.
- 자산 테스트는 디코딩, 정적 참조, alpha, optical bbox, 중복, 미사용 precache를 검사한다.
- 오래된 `scripts/*.spec.ts`는 현재 계약과 Node 해석 방식에 맞게 공식 `tests/` 게이트로 이관하거나 삭제 근거를 문서화한다.
- 전체 `npm run typecheck`, `node --test tests/*.test.*`, `npm run build`, `npm audit --audit-level=high`, Android `lintDebug`, `assembleDebug`를 실행한다.

### 브라우저

- 공개·부모·아이·공용·기능 route를 360×800, 390×844, 412×915과 데스크톱 폭에서 확인한다.
- 키보드 전용, 200% 확대, reduced motion, 긴 한국어, 빈 데이터, 네트워크 지연·실패, modal focus, 이미지 decode, console error를 확인한다.
- 로그인·저장·재시도 버튼의 spinner, 중복 탭 방지, timeout 복구를 실제 상호작용으로 확인한다.
- route lazy loading 중 공백이나 layout shift가 없는지 느린 네트워크로 확인한다.

### Android 실기기

- A17 `RFKL40DP73J`: 부모 모드의 로그인 유지, 홈·가족·위치·일정·메모·보고서·설정과 앱 재개를 검증한다.
- razr: 아이 모드의 기존 페어링과 세션을 보존하고 홈·경로·준비물·메모·위치 상태·SOS 진입·앱 재개를 검증한다.
- 두 기기 모두 `adb install -r`만 사용하고 앱 데이터 삭제, 계정 재로그인 강요, refresh 토큰 조작을 하지 않는다.
- S25는 설치·실행·로그·세션 조회에서 제외한다.

## 실행 웨이브

### 웨이브 1: 기능·상태 신뢰성

로그인 검증과 제한시간, 공통 busy/error/status, 보고서의 정직한 오류 처리, 아이 경로 route, 안전한 뒤로가기, modal 접근성을 먼저 수정한다. 이 웨이브는 시각 토큰 이행 전에 기능적으로 독립 검증 가능해야 한다.

### 웨이브 2: 디자인 기반·자산

타이포·색·간격·radius·shadow·아이콘·터치 타깃 토큰을 확정하고 공통 component에 적용한다. 체크무늬·optical balance·미사용·중복 자산을 정리하고 회귀 검사를 추가한다.

### 웨이브 3: 전체 화면 이행·성능·출시 검증

부모·공용 출시 화면, 아이 화면, 프로덕션 gate 안쪽 선생님 화면 순으로 공통 토큰과 상태 component를 적용한다. route lazy loading과 PWA 자산 최적화를 마친 뒤 전체 브라우저·Android·배포 검증을 수행한다.

각 웨이브는 자체 테스트가 통과하는 작은 커밋으로 나눈다. 최종 통합 전에 전체 자동·브라우저·기기 게이트를 다시 실행한다.

## 완료 기준

- 알려진 P0/P1 기능 결함이 남지 않는다.
- 성공한 빈 응답과 실패한 조회가 UI에서 구분된다.
- 사용자가 시작한 비동기 행동은 즉시 진행 상태를 보이고 timeout·실패 후 복구 가능하다.
- 부모·아이 역할 route와 활성 아이 불변식이 테스트와 실제 상호작용에서 유지된다.
- 핵심 텍스트 대비는 WCAG 2.2 AA, 모든 interactive target은 제품 기준 44×44px 이상, 키보드 focus는 가시적이다.
- 핵심 타이포 9단계, 아이콘 5단계, spacing·radius·shadow 토큰을 벗어난 예외에는 근거가 있다.
- 이미지 깨짐·체크무늬·optical imbalance·불필요한 PWA 자산이 없다.
- typecheck, 전체 테스트, build, audit, Android lint/build가 모두 통과한다.
- 360×800부터 데스크톱까지 주요 route에 overflow·겹침·console error가 없다.
- A17 부모 모드와 razr 아이 모드에 최신 APK를 데이터 보존 방식으로 설치하고 각 역할의 핵심 동선을 확인한다.
- 최종 변경을 현재 브랜치에서 커밋하고 `main`에 반영한 뒤 원격 `origin/main`과 커밋이 일치함을 확인한다.

이 기준을 모두 통과하고 알려진 결함·검증 공백이 없을 때만 이번 범위의 출시 준비도를 100/100으로 보고한다.
